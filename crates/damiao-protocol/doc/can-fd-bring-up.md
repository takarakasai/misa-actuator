# CAN-FD 立ち上げ状況 (PCAN + DM-J4310)

2026-08-02、PCAN-USB Pro FD + DM-J4310-2EC で実施。

## 結論 (2026-08-02 追記: CAN-FD 動作確認完了)

**モータ側を 5 Mbps に設定した結果、CAN-FD の送受信とも実機で動作した。**
`PMAX`/`VMAX`/`TMAX` を FD 経由で読み出し、`--refresh-limits` で MIT スケールに
反映するところまで確認済み。

```
> damiao-cli -i "pcan:usb1@1M,5M" --fd -m 16 --refresh-limits info
MIT ranges from motor registers: PMAX=12.5 VMAX=30 TMAX=10
```

以下は設定前 (モータが classic のみだった時点) の切り分け記録。手順自体は
「FD で応答しない」場面で再利用できる。

## 実機構成

| | |
|---|---|
| モータ | DM4310 (レジスタレイアウト J4310) |
| CAN_ID | **16 (0x10)** — 既定の 1..8 スキャン範囲の外 |
| MST_ID | 0 |
| ビットレート | classic 1 Mbps |
| PMAX / VMAX / TMAX | **12.5 / 30 / 10** |

`PMAX`/`VMAX`/`TMAX` が読めるので、**DAMIAO 側は真のモデル自動検出が成立する** —
これらのレジスタが MIT 量子化レンジそのものであり、機種を推測する必要が無い
(RobStride との決定的な違い)。

## 切り分け

| 実行 | 結果 |
|---|---|
| classic (`-i pcan:usb1@1M`) | **全レジスタ読み出し成功** |
| `--fd` (`@1M,5M`) | 全タイムアウト |
| `--fd` (`@1M,2M`) | 全タイムアウト |
| **`--fd-link-classic-frames` (`@1M,5M`)** | **全レジスタ読み出し成功** |

最後の 1 行が決め手。リンクを `CAN_InitializeFD` で 1M/5M として開いたうえで、
フレームだけ classic で送るとモータは普通に答える。よって:

- `CAN_InitializeFD` は成功している
- 80 MHz クロックから導出したビットタイミング文字列をアダプタが受理している
- FD チャネルでの受信経路は動いている
- **FD フレームだけが理解されない → モータが FD ノードでない**

この切り分けのために `--fd-link-classic-frames` を追加した。診断専用で、運用で使う
モードではない。「モータが FD 非対応」と「こちらの FD 実装が壊れている」は次に取る
行動がまったく違うので、推測で済ませてはいけない。

## FD 有効化後に判明したこと

### 1. classic は使えなくなる

モータを FD ノードにすると、**classic 初期化では一切通信できなくなる**
(実測 36/36 タイムアウト)。モータが FD フレームで応答し、classic コントローラは
それをエラーフレームとして扱うため。想定どおりの挙動だが、切り替え後に classic で
試して「壊れた」と誤解しないこと。

### 2. レジスタ読みが約 1/7 の確率で無応答になる

FD 化直後の実測: 6 レジスタ x 複数回で 11〜15% が無応答。特徴:

- **ランダムなレジスタ**で発生 (特定 RID ではない)
- **タイムアウトを 100ms → 1000ms にしても失敗数が変わらない** → 遅いのではなく
  応答が来ていない
- **アダプタはバスエラーを一切報告しない** (`PCAN_ERROR_BUSLIGHT`/`BUSHEAVY`/
  `BUSOFF`/`BUSPASSIVE` いずれも 0)
- 送信は毎回全フレーム成功
- classic では発生しない

ホスト側の問題を示す兆候が無く、要求が FD 速度で届くようになった結果モータの
ファームウェアが取りこぼしていると解釈するのが妥当。

**対応**: `read_register` に 3 回までの再送 + 5ms のギャップを入れた
(`REGISTER_READ_ATTEMPTS` / `REGISTER_RETRY_GAP`)。レジスタ読みは副作用が無いので
再送に危険が無く、呼び出し側に「もう一度聞け」という意味しか持たない
タイムアウトを返すよりよい。**修正後は 60/60 成功。**

### 3. 副産物: PCAN 受信のフレーム取りこぼしを修正

`try_read` がエラー/ステータス/RTR フレームを弾いたときに `Ok(None)` を返していた。
呼び出し側はこれを「キューが空」と解釈して自動リセットイベントを待つが、目的の
フレームが既にキューにあってもイベントは再発火しないため、次の到着まで見つからない。
`ReadOutcome::{Frame,Empty,Skipped}` に分け、`Skipped` では待たずに読み直すよう修正。

## 検証済み / 未検証

**検証済み** (実機): FD リンク初期化、80MHz からのビットタイミング導出、
FD フレームの送信・受信、レジスタ読み出し、`--refresh-limits`。

`TPCANMsgFD` のメモリレイアウト (size 72 / offset 0,4,5,6) と DLC 変換はユニット
テストで固定済み。DAMIAO のペイロードは classic/FD とも常に 8 バイトなので
`len_to_dlc(8) = 8` となり、padding や 12..64 バイトの特殊 DLC 経路には入らない
(= そこは未検証のまま)。

### 4. FD でのモータ駆動 — 動作確認済み

```
> damiao-cli -i "pcan:usb1@1M,5M" --fd -m 16 --refresh-limits move-to -0.372 --speed 1.0 --duration 2
pos=-0.397 vel=+0.183 tau=+0.105
pos=-0.379 vel=+0.212 tau=+0.051
pos=-0.374 vel=+0.007 tau=+0.120
pos=-0.372 vel=-0.007 tau=+0.090   ← 目標到達
note: 8 of 48 feedback reads went unanswered (tolerated)
```

MIT (トルクゼロ保持) と POS_VEL (往復) の両方で確認。速度プロファイルと
トルクの推移も期待どおり。

**制御ループはフィードバック欠落を許容する必要がある。** 上記のとおり FD では
1/7 程度が返らないので、1 回の欠落で中断すると 1 秒の保持すら完走しない。
最初にこれを踏んだとき、**指令自体は効いていてモータは動いていた**のに
「応答なし」に見えたため、通信不能と誤解しかけた。

`control_loop` は連続 5 回 (10ms 周期 = 50ms) まで許容し、それを超えたら停止する。
孤発の欠落と「モータが黙った」は区別しなければならない — 観測できない相手を
命令し続けるのは暴走を見逃す道なので。欠落数は実行後にまとめて報告する。

## 検証済み / 未検証 (最終)

**検証済み** (実機): FD リンク初期化、ビットタイミング導出、FD フレーム送受信、
レジスタ読み出し、`--refresh-limits`、**MIT 制御**、**POS_VEL 位置制御**。

**未検証**: 12..64 バイトの特殊 DLC 経路 (DAMIAO は常に 8 バイトなので通らない)、
FD での chirp / characterize などの長時間実行。
