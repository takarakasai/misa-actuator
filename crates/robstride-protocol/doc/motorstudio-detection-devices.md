# motorstudio の "Detection Devices" は何をしているか

motorstudio 0.0.13 が `motor type RS04` / `motor type EL05` を表示する仕組みの調査。
2026-08-02、PCAN-USB Pro FD を同一バスに載せ `robstride-cli dump` で捕捉した
実トラフィックと、同ツールの "Read Para" 出力に基づく。

## 1. 捕捉した生データ (RS-04, id=1)

```
   t [ms]          id  comm type               target    data
 4182.229  0x0000FD01   0 GetDeviceId            1 <-0x00FD  00
 4182.696  0x000001FE   0 GetDeviceId          254 <-0x0001  C3 5C 3B C0 00 20 30 0F
 4189.176  0x0400FD01   4 Disable                1 <-0x00FD  00 C4 00 00 00 00 00 00
 4189.437  0x020001FD   2 OperationStatus      253 <-0x0001  00 C4 56 00 04 01 20 07
 4196.434  0x0000FD09   0 GetDeviceId            9 <-0x00FD  00
```

`Detection Devices` の押下から表示までに飛んだのは **これだけ**。パラメータ読み
(comm type 17 / 19) は一切無い。

## 2. フレームごとのパース

### 2.1 `0x0000FD01` — GetDeviceId 要求

| ビット | 値 | 意味 |
|---|---|---|
| 28~24 | `0x00` | comm type 0 = Get device ID |
| 23~8 | `0x00FD` | ホスト CAN ID = 253 |
| 7~0 | `0x01` | 対象モータ ID = 1 |

データは `00` (DLC=1)。マニュアルは 8 バイトのゼロと書いているが、実装は 1 バイト
しか送っていない。モータは受け付けている。

### 2.2 `0x000001FE` — GetDeviceId 応答

| ビット | 値 | 意味 |
|---|---|---|
| 28~24 | `0x00` | comm type 0 |
| 23~8 | `0x0001` | 応答したモータの CAN ID = 1 |
| 7~0 | `0xFE` | 固定値 (マニュアル記載どおり) |

データ `C3 5C 3B C0 00 20 30 0F` = 64-bit MCU UID。

**バイト順**: motorstudio のステータス行は `mcuId:0Xf302000c03b5cc3` と表示する。
16 桁に揃えると `0F302000C03B5CC3`。これは受信バイト列を**逆順**に読んだ値:

```
受信順   C3 5C 3B C0 00 20 30 0F
逆順     0F 30 20 00 C0 3B 5C C3   → 0x0F302000C03B5CC3 ✓
```

つまり UID はリトルエンディアンの u64 として表示されている。

### 2.3 `0x0400FD01` — バージョン読み **要求** (マニュアル: comm type 26)

| ビット | 値 | 意味 |
|---|---|---|
| 28~24 | `0x04` | **`4`。`DISABLE` と同じ値** |
| 23~8 | `0x00FD` | ホスト ID |
| 7~0 | `0x01` | 対象モータ ID |

データ `00 C4 00 00 00 00 00 00`。マニュアルの type 26 要求は
`Byte[0]=0x00, Byte[1]=0xC4` で **一致**。

マニュアルの comm type 欄が `0x4` になっているのを、本リポジトリでは以前
「コピペミス、本来 `0x1A`」と注記していた。**実機はマニュアルどおり**で、注記の方が
誤りだった。訂正済み。

→ **ID だけでは Disable と区別できない。`00 C4` プレフィックスが唯一の識別子。**

### 2.4 `0x020001FD` — バージョン読み **応答**

| ビット | 値 | 意味 |
|---|---|---|
| 28~24 | `0x02` | **`2`。通常のフィードバックと同じ値** |
| 23~8 | `0x0001` | モータ CAN ID |
| 7~0 | `0xFD` | ホスト ID |

データ `00 C4 56 00 04 01 20 07`:

| バイト | 値 | 意味 |
|---|---|---|
| 0~2 | `00 C4 56` | 固定プレフィックス (マニュアル記載と一致) |
| 3~6 | `00 04 01 20` | 0, 4, 1, 32 → **`0.4.1.32`** |
| 7 | `07` | **マニュアルに記載なし** |

`0.4.1.32` は motorstudio が `AppCodeVersion` 欄に表示した値と完全一致。

→ **応答も通常フィードバックと ID が同じ。`00 C4 56` でしか区別できない。**
これを取り違えると、位置・速度・トルクとして「それらしい数値のゴミ」になる。

### 2.5 `0x0000FD09` — id=9 への GetDeviceId

応答なし。ツールが ID を順に走査している。

## 3. EL05 側の "COM send Data" も同じものだった

EL05 のスクリーンショットに `COM send Data: 41540007e84c01000d0a` とある。これは
CAN ではなく USB-CAN モジュールの **AT プロトコル**のフレーミング:

```
41 54          "AT"
00 07 E8 4C    32-bit = (CAN_ID << 3) | flags
01             DLC
00             データ
0D 0A          "\r\n"
```

`0x0007E84C >> 3 = 0x0000FD09`、下位 3 ビット = `0b100` (拡張フレームフラグ)。

`0x0000FD09` = **comm type 0 / ホスト 0xFD / 対象 9**。DLC 1、データ `00`。

これは §2.5 で捕捉した RS-04 側の最終フレームと**完全に同一の形**。つまり:

- AT フレーミングの解釈が正しいことが裏取りできた
- EL05 でも RS-04 でも `Detection Devices` は同じ走査をしている
- 両機種とも id=9 付近まで探って止まっている

## 3.5 EduLite05 の捕捉 (同一手順、id=1)

```
 7149.131  0x0000FD01   0 GetDeviceId            1 <-0x00FD  00
 7154.644  0x000001FE   0 GetDeviceId          254 <-0x0001  62 0A 30 21 18 31 B6 06
 7155.902  0x0400FD01  26 VersionRead(req)       1 <-0x00FD  00 C4 00 00 00 00 00 00
 7156.160  0x020001FD  26 VersionRead(rsp)     253 <-0x0001  00 C4 56 0A 05 00 01 07
 7161.243  0x0000FD09   0 GetDeviceId            9 <-0x00FD  00
```

**RS-04 と完全に同じシーケンス。** フレーム数も順序も同じで、違うのは応答の中身だけ。

### UID (バイト順の再確認)

```
受信順   62 0A 30 21 18 31 B6 06
逆順     06 B6 31 18 21 30 0A 62   → 0x06B6311821300A62
```

motorstudio の表示 `mcuId:0X6b6311821300a62` と一致。§2.2 のバイト順が 2 台目でも
成立。

### バージョン応答の比較

| | Byte3~6 | 十進 | Byte7 |
|---|---|---|---|
| RS-04 | `00 04 01 20` | 0.4.1.32 | **`07`** |
| EduLite05 | `0A 05 00 01` | 10.5.0.1 | **`07`** |

**Byte7 は両機種とも `0x07`。** MIT スケールが 21.8 倍違う 2 台で同値なので、
**モデルコードではない**。`00 C4 56` + バージョン 4 バイト = 7 バイトなので、
「有効バイト数」を示す固定マーカーと解釈するのが素直。

なお EL05 の `AppCodeVersion` 文字列欄は `1.0.5.0.1` (5 成分) だが、バージョン応答は
`10.5.0.1` (4 成分)。数字の並びは `1 0 5 0 1` で共通なので同一リリースの別表記と
思われる。RS-04 側は `0.4.1.32` で文字列とバイナリが完全一致していた。

## 4. で、機種名はどこから来るのか

`Detection Devices` から表示までにバス上を流れたのは **GetDeviceId と バージョン読み
だけ**。パラメータ読みは無い。よって `RS04` / `EL05` の出どころは次のいずれか:

**バージョン番号のマイナー成分が機種番号である。** RobStride 公式のファームウェア
配布物 (`github.com/RobStride/Product_Information` の releases) がその対応を
そのまま示している:

| 配布ファイル | バージョン | マイナー |
|---|---|---|
| `rs00-0.0.3.32.bin` | 0.**0**.3.32 | 0 |
| `rs01-0.1.3.18.bin` | 0.**1**.3.18 | 1 |
| `rs02-0.2.3.34.bin` | 0.**2**.3.34 | 2 |
| `rs03-0.3.1.42.bin` | 0.**3**.1.42 | 3 |
| **`rs04-0.4.1.32.bin`** | 0.**4**.1.32 | 4 |
| `rs05_0.5.0.14.bin` | 0.**5**.0.14 | 5 |
| `rs06_0.6.0.12.bin` | 0.**6**.0.12 | 6 |

実機 RS-04 が返した `0.4.1.32` は `rs04-0.4.1.32.bin` と**完全一致**。
実機 EduLite05 の `10.5.0.1` も同じ規則で読める — メジャー `10` が EduLite ライン、
マイナー `5` が 05。**これで motorstudio の `RS04` / `EL05` 表示が両方とも説明できる。**

| 成分 | 意味 |
|---|---|
| メジャー | 製品ライン。`0` = RS、`10` = EduLite |
| **マイナー** | **機種番号** |
| 以降 | ビルド |

| 候補 | 判定 |
|---|---|
| **(b) バージョン番号** | **確定** — 公式配布物 7 件 + 実機 2 台で裏付け |
| (a) バージョン応答 Byte7 | 否定 — RS-04 / EL05 とも `0x07` |
| (c) MCU UID | 不要 |
| (d) 既定表示 | 不要 |

`AppCodeName` は出どころではない。検出時に読んでいないうえ、RS-04 の値は `motor`
で機種情報を持たない。

### 実装

`MotorModel::from_firmware_version([u8; 4])` → `(MotorModel, ProductLine)`。
メジャーがラインを、マイナーが機種を決める。ラインは呼称にしか影響しない
(EduLite05 は RS-05 と同一ハードウェアで MIT スケールも同一、両マニュアルで確認済み)。

未知のラインや機種番号は `None` を返す。証拠の厚みが揃っていないことは明記しておく:
RS ラインは公式配布物 7 件 + 実機一致、EduLite ラインは実機 1 台が同じ構造に
従っていること。

実機での動作:

```
> robstride-cli -i pcan:usb1 -m 1 identify          # --model 無し
version read (comm type 26): 10.5.0.1  [trailing byte 0x07]  → EduLite05
VERDICT: the motor identifies as RS-05. Use --model RS-05.

> robstride-cli -i pcan:usb1 --model RS-04 -m 1 identify
VERDICT: the motor identifies as RS-05, but this session opened as RS-04.
         Use --model RS-05 — MIT scaling is wrong until you do.
```

## 5. 実装への反映

- `build_version_read_frame` / `parse_version_reply` — §2.3/2.4 の生バイトを
  そのままユニットテストに固定
- `is_version_request` — `dump` が Disable と誤ラベルしないための判定
- `Motor::read_version()` — 接続時チェックで使用。文書化済み・往復 1 フレーム
- `VersionReply::trailing` — Byte7 を捨てずに保持。意味不明のまま握り潰すと
  §4 の切り分けができなくなる

**モデル判別自体は Byte7 の解明を待たずに実用水準に達している。** 古典パラメータ
空間の `0x700B limit_torque` が RS-04 で 115 N·m を返し、これを MIT で表現できるのは
family 中 RS-04 のみ (次点の RS-03/06 は 60)。詳細は
`param-table-firmware-divergence.md`。
