# 摩擦と負荷の測定 — 3 つの run の違い

Characterize タブ（および `robstride-cli characterize`）には摩擦・負荷に関わる run が
3 つある。どれも「関節が重い」を数値にするが、**何を固定して何を測るか**が違うので、
得られる量も、信用できる条件も、失敗の形も違う。

このファイルは 2026-08-06 に実機で 3 つを回した際、区別が UI のヒントだけでは
足りなかったので書いた。

---

## 1. 一覧

| | Load map | Breakaway | Breakaway map | Velocity sweep |
|---|---|---|---|---|
| 日本語 | 負荷マップ | 静止摩擦 | 静止摩擦の角度依存 | 動摩擦 |
| 指令 | **位置**（段階的） | **トルク**（ランプ） | 位置 → トルクランプ | **速度**（一定・低速） |
| 測定中の軸 | 各点で**静止** | **静止 → 動き出す瞬間** | 各位置で同じ | **等速で運動中** |
| 制御モード | Position | Torque（または MIT） | Position + Torque | Velocity |
| 直接得る値 | 保持トルク(位置) | 動き出したトルク | 動き出したトルク(位置) | 運動中のトルク(位置) |
| 主目的 | **負荷**（重力・ばね） | **起動トルク** | **起動トルクの角度分布** | **転がり抵抗** |
| 摩擦の求め方 | 往復の**ヒステリシスの半分** | 閾値そのもの | 両方向の**差の半分** | 往復の**差の半分** |
| 結果の形 | 曲線（位置依存） | スカラ（方向ごと 1 個） | 曲線（位置依存） | スカラ + 位置ビン |
| 所要時間 | 中 | **短** | **最長** | 中 |
| 実装 | `run_load_map` | `run_breakaway` | `run_breakaway_map` | `run_velocity_sweep` |

## 2. 物理的な違い

**静止摩擦（stiction）> 動摩擦** が通常の関係。止まっている軸を動かし始めるトルクは、
動き続けさせるトルクより大きい。

この差が**低速でのスティックスリップ（ジャダー）**の原因になる。速度を上げると摩擦が
一旦落ちる（Stribeck 効果）ので、**低速域だけが不安定**という挙動になり、
速度制御のゲインを上げても直らない。摩擦の測定が制御の前に来る理由がこれ。

- **Breakaway** は「静止 → 運動」の**遷移**を捉える。閾値なので 1 run で 1 個。
- **Velocity sweep** は運動を**維持**する抵抗。等速なので慣性項が消える
  （だから低速が必須 — 速いと測っているのが摩擦ではなく慣性になる）。
  往路と復路でトルクの**符号が反転する成分が摩擦**、反転しない成分が負荷。

### なぜ往復が必要か

等速運動中のトルクは `負荷 ± 摩擦` である。片道だけでは

```
τ_out  = load + friction
```

の 1 式しかなく、2 つの未知数を分離できない。復路を取ると

```
τ_back = load - friction
```

が加わり、**半差が摩擦、半和が負荷**として解ける。だから `return_sweep` は既定 on で、
off にした場合は結果に「分離できていない」と明記される（黙って片道の値を摩擦と
呼ばない）。

## 3. Load map が他の 2 つと違う点

**Load map は本来「摩擦を測る run」ではない。** 目的は**位置に対する負荷** —
重力トルクやばねトルクの形と、それが釣り合う位置（equilibrium）。摩擦はヒステリシス
として**副産物**で出る。

その摩擦は静止摩擦寄りである。各停留点で軸は止まっており、モーターは負荷 + stiction と
釣り合っているため。ただし Breakaway と違って**閾値までは押していない**ので、
「動き出すのに必要な値」より小さく出る。

そして **Load map だけが位置依存性を見せる。** 他の 2 つは 1 つの数値、Load map は曲線。
重力負荷は姿勢の関数なので、これは他の run では代替できない。

### equilibrium の 2 種類

- `equilibrium_position_rad` — 保持トルクが 0 を横切る位置。摩擦を含む。
- `static_equilibrium_position_rad` — **往復の中線**が 0 を横切る位置（de-frictioned）。
  摩擦を除いた真の釣り合い点。重力補償の基準にするならこちら。

範囲内で符号が変わらなければどちらも `None` になる。これは失敗ではなく
「掃引範囲の中に釣り合い点が無い」という範囲についての事実。

## 3.5 角度依存性

摩擦は角度で変わる。軸受のプリロード、シールの接触、歯のかみ合いはどれも 1 回転の
中で変化するので、**1 姿勢で特性を取ると、可動範囲の他のどこでも間違っている数値**で
関節を説明することになる。4 つの run はいずれも角度依存を扱えるが、扱い方が違う。

| run | 角度依存の扱い |
|---|---|
| Load map | **構造的に角度依存**。`static_load_curve()` が位置ごとの `(位置, 負荷, 摩擦)` を返す |
| Velocity sweep | **位置でビン分割**。`friction_curve(bins)` が位置ごとの動摩擦。GUI がプロットしている |
| Breakaway map | **位置ごとに両方向ランプ**。`BreakawayMapPoint` が位置・正方向・負方向・`rested` を持つ |
| Breakaway | **単一姿勢のみ**。角度依存は見えない |

GUI はどの run でも要約に**角度方向のばらつき**を出す:

- Load map → `friction over angle` に最小〜最大
- Breakaway map → `stiction over angle` に最小〜最大、および
  `angle dependence`（幅を平均で割った百分率）

**`angle dependence` が平均に対して大きければ、1 つの数値ではこの関節を記述できない**
というのがその run の結論であって、結論に付ける注意書きではない。

なお `mean_friction_nm()` のような平均値は角度依存を捨てた値なので、
重力補償やフィードフォワードの設計に使うなら曲線側を見ること。



| 知りたいこと | run |
|---|---|
| 重力補償のトルク / 釣り合う姿勢 | **Load map** — ただし**出力側に負荷が付いていることが前提**（下記）|
| 静止状態から動き出すか、サーボの最小指令 | **Breakaway**（1 姿勢で足りるとき） |
| 起動トルクが姿勢でどう変わるか | **Breakaway map** |
| 動かし続けるコスト、効率、低速追従性 | **Velocity sweep** |
| 上の 3 つが機能する前提（トルクが 0 で返る機種） | **Measure Kt** |

## 4.5 Load map は負荷が付いていないと意味がない

**水平で、出力側に何も付いていない状態で Load map を回しても得るものはほとんどない。**
本来の目的（負荷の位置依存と釣り合い位置）に対して、**測る対象が存在しない**。

摩擦の計測器としても、この 4 手法で最も弱い。§3 のとおり Load map が測るのは
**摩擦の帯の内側で、到来方向によって実際に生じた差**であって、**帯の幅そのものでは
ない**。位置ループが誤差を強く追い込めばトルクは帯の内側に押し込まれるので、

```
Load map の摩擦  ≤  真のスティクション
```

が定義から従う。等号は両方向とも帯の縁で釣り合ったときだけ。**摩擦の大きさを知りたい
なら Breakaway map（帯の縁を直接測る）を使う。**

2026-08-07 の RS-03（水平・無負荷）で Load map が 0.113 N·m を返し、同じ関節の
Breakaway map が 1.180 N·m だったのは、この不等式の範囲内である。そして
**シミュレータで裏が取れている**（§7 の訂正記録）: 無負荷で位置誤差が詰まれば
モーターは何も出す必要がなく、往復とも保持トルクは 0 に近づき、半差も 0 に向かう。

つまり **0.113 N·m は故障ではなく、無負荷関節に対する Load map の正しい振る舞い**
である。低いのは関節の性質ではなく**手法の性質**。`worst dwell spread` が peak を
超えていた事実は別問題として残る（トルクが小さいほど spread 比は大きく見える点も
効いている可能性がある）。

**Load map が要るのはリンクやアームを付けた後、あるいは垂直軸**。そこでは
重力トルク対角度がフィードフォワードにそのまま必要になる。

### 無負荷でも半和はゼロにならない — コギング

**コギングトルクは位置の関数だが、進行方向で符号が反転しない。** したがって
重力やばねと同じく**半和の側に乗る**。水平・無負荷の RS-03 で velocity sweep が
`LOAD (HALF-SUM) 0.334 N·m` を報告したのはこれ（+ ケーブルの張り）の可能性が高い。

つまり**無負荷の「負荷」測定はコギングの測定になる**。それはフィードフォワードの
実項なので、知る価値はある — ただし重力負荷と読み違えないこと。

## 5. 相互チェック

3 つは独立に同じ関節を測るので、値の整合が測定自体の検証になる。**同じ個体で
3 つ揃えたときに**次が成り立つはず:

```
breakaway  ≳  load map の摩擦  ≳  velocity sweep の動摩擦
```

**2026-08-07、3 個体・2 機種で成立を確認した:**

| 個体 | 静止摩擦 | 動摩擦 | 比 |
|---|---|---|---|
| RS-03 (id 96) | 1.180 | 0.728 | 1.62 |
| RS-04 (id 2) | 0.943 | 0.761 | 1.24 |
| RS-04 (id 3) | 0.595 | 0.516 | 1.15 |
| **RMD-X4-P36-36 (id 1)** | **0.647** | **0.268** | **2.41** |

**1 個体の偶然ではなく、1 ベンダーの癖でもない。** 比は 1.15〜2.41 に散る
（Stribeck の落差は関節ごとに違う）が、**順序は 4 個体・3 機種・2 ベンダーすべてで
保たれた**。RMD-X4 は落差が最大で、低速でのスティックスリップが最も起きやすい。

どちらかの測定が壊れていれば破れる関係なので、これは両方の妥当性を支持する。
逆に、**同じ関節で静止摩擦 0.647（低く偏った値、§7）と動摩擦 0.728 を並べると
不等式は破れる** — 偏りの検出にも使える。

**中項（Load map）は同じ日に取ったが 0.113 N·m で、不等式を破った。**
これは Load map 側が壊れていたためで、原因も画面に出ていた
（`hunting, not settling`）。§7 に詳細。**チェックが実際に不良を捕まえた例**として
残す価値がある — 3 つの数値が揃うことより、揃わないときに気づけることが目的なので。

- `breakaway < velocity sweep` なら、どちらかが間違っている。よくある原因は
  velocity sweep の速度が高すぎて慣性を測っている、または breakaway のランプが
  速すぎて動き出しを見落としている。
- `load map の摩擦` が他の 2 つから大きく外れるなら、まず **worst dwell spread**
  を見る（§7）。

## 5.5 MyActuator は Kt を測れない — 測る必要もない

**この family はトルクと電流が独立していない。** `torque_nm` はワイヤの値ではなく、
**設定した Kt で電流から計算した値**である（`myactuator-driver/src/driver.rs`:
「Output torque in N·m = `current_a · Kt`」）。

したがって Kt run を回しても**恒等写像を測るだけ**で、`Kt = 1.0000`、`R² = 1.0000` が
返る。2026-08-08 に RMD-X4-P36-36 で実際にそうなった。**この 1.0000 は測定値ではなく、
「単位が N·m ではなくアンペアである」ことの指紋**である。

RobStride で測れるのは **MIT のトルクと `IqFilt` の電流という 2 経路が独立**していて、
片方（`MeasuredTorque`）が壊れていても他方が生きているから。MyActuator は経路が
1 本しかない。外部トルクセンサか既知の錘が無ければ実測できない。

**が、モーターが値を持っている。** `KT_OUT`（`0xC0[0x3E]`）を読めばよい。
**2026-08-08、RMD-X4-P36-36 の実測: `kt_out = 1.1 N·m/A`、`reduction_ratio = 36`。**

**独立した裏付け**: 同じブロックの `rated_current = 8.62 A` と掛けると
8.62 × 1.1 = **9.5 N·m** で、この機種の定格トルクとして妥当。無関係な 2 つの
レジスタが整合するので、この値は信用できる。

**注意**: `KT_OUT` は**非公開の `0xC0` ブロック**にあり、Params タブの
`INCLUDE UNDOCUMENTED SPACES` の向こう側にある。既定でオフなのは、
**RobStride のバルクテーブルで 2 回モーターが無応答になった**ため（§6）。
MyActuator の `0xC0` に事故の記録は無いが、**接続ごとに自動で読むかどうかは
別の判断**であり、既定でそうするのはこの注意と矛盾する。

### 単位が電流のときの読み替え

2026-08-08 の RMD-X4-P36-36（Kt 未設定 = 電流単位モード）の結果:

| 画面表示（実際は A） | × 1.1 した真の値 |
|---|---|
| 動摩擦 0.268 | **0.295 N·m** |
| 負荷 0.028 | 0.031 N·m |
| breakaway `not reached below 0.500` | **0.55 N·m まで押した** |

動摩擦 0.295 N·m に対して 0.55 N·m では静止摩擦にわずかに届かず、破断しなかったのは
筋が通る（§5 の不等式より静止摩擦 > 0.295）。

## 6. 前提: トルクフィードバック

**3 つすべてトルクフィードバックが前提。** ところが RobStride の一部ファームは
`MeasuredTorque`（`0x302C`）を**定数 0** で返す（handover.md §4）。その状態では

- 摩擦は 0 と報告される（「摩擦の無い関節」ではなく「測れていない」）
- 安全 envelope のトルク上限は**何も監視していない**（0 は常に上限内）

対策は `torque = current × Kt` で合成すること。`IqFilt`（`0x701A`）は同じファームでも
動くので、Kt があれば復元できる。

Kt は **Characterize タブの Measure Kt ボタン**で測れる（結果は Kt 欄に自動で入る）。
run の間だけ電流報告と Kt が有効になり、終了時に戻る — 電流読み出しは RobStride では
追加トランザクションでループ速度がほぼ半分になるため、chirp などに残さない。

CLI なら `robstride-cli characterize kt`（パラメータを細かく指定できるのはこちら）。

### Kt 測定にリーシュが必要な理由

自由軸ではトルクレベルを保持できず、電流が整定しない。整定しない電流には
フィットする傾きが無い。そのため各レベルを **MIT の位置保持（リーシュ）**に対して
印加する。

リーシュの剛性は**振幅から導出**される（`kt_leash`）。ピークトルクでの定常たわみが
安全 envelope の位置窓（±0.5 rad）の 40% を超えないところまで kp を上げる。
固定ゲインにしていた時期に、振幅 7.2 N·m を kp 8 に対して指令して
たわみ 0.9 rad で位置窓に弾かれ、1 点しか記録できずに失敗した（2026-08-06, RS-04）。

振幅自体も 1.5 N·m で上限を切っている。**Kt は線形領域の性質**で、飽和すると Kt は
下がるため、大振幅は危険なだけでなく**より悪い値を測る**。

## 7. 結果を信用してよいかの判定

### Load map: worst dwell spread

各停留点でのトルクの p-p 振れ。これが **peak holding torque と同程度以上なら
軸が静止していない** — その点は「静定した負荷」ではなく**リミットサイクルの平均**。
GUI はこの場合 `hunting, not settling` と明記する。

対策は `settle` を伸ばす（0.3 → 1.0 s）。それで spread が peak を下回れば数値を
信用できる。

**実例（2026-08-06, RS-04）**: spread 0.783 N·m に対し peak 0.559 N·m。
摩擦 0.35 N·m という読みは出たが、往路の点が滑らかな曲線にならず散っており、
**暫定値として扱うべき**もの。settle を伸ばして取り直す必要がある。

### 静止摩擦が大きい関節では Load map が成立しないことがある

**2026-08-07, RS-03 (id 96)**: spread **1.276 N·m** に対し peak 0.806 N·m。
摩擦 **0.113 N·m** — 同じ関節の動摩擦 0.728 の **6 分の 1**。§5 の不等式が破れる。

**観測されている事実**は 2 つだけ: spread が peak を超えて `hunting` 判定が出たこと、
そして摩擦が動摩擦の 6 分の 1 に出たこと。

**仮説（未検証）**: この関節は静止摩擦が 1.180 N·m あり、位置制御でそれと戦わせると
スティックスリップのリミットサイクルが避けられず、停留中の振動が往路・復路の
ペアリングで平均されてヒステリシスが潰れる。

> **仮説は不要だった。シミュレータでの検証が別の答えを出した — §4.5 の構造で足りる。**
>
> `plant.rs` のフィードバックトルクは `applied_torque_nm`、つまり**モーターが出した
> トルク**で、摩擦は含まない。これは実機と同じ（トルクセンサも電流由来のトルクも
> モーター出力を報告する）。そして軸が `stuck` の間、駆動トルクが静止摩擦以下なら
> 動かない。
>
> したがって**無負荷で位置誤差がゼロに詰まったあと、モーターは何も出す必要がない** —
> 摩擦が軸を保持する。往路も復路も `τ_motor ≈ 0` なので**半差も 0**。
> **シミュレータは壊れておらず、実機の挙動を再現している。** Load map が
> 帯の「内側」を測るという §4.5 の構造がそのまま出ているだけで、
> **ハンチングを持ち出す必要はない。**
>
> 以下は当初その点を誤読した記録。
> 摩擦を 0.2 / 0.5 / 1.0 / 2.0 N·m と植えて 3 手法を比較したところ、Breakaway は
> 4 点すべてで植えた値を回収した（0.210 / 0.506 / 1.005 / 2.006）が、
> **Velocity sweep と Load map は摩擦の大きさに関係なく一律 0.000** だった。
> 仮説が正しければ小さい摩擦では回収できるはずで、そうならなかった。
>
> **Velocity sweep が 0 になる理由は未解明のまま。** 等速運動中はモーターが動摩擦を
> 出し続けるので ±μ が出るはずで、こちらは上の説明では片づかない。実機では同じ run
> が 0.728 N·m を回収している。実験は
> `crates/misa-actuator-sim/tests/sysid_recovers_planted_values.rs` に `#[ignore]`
> で残してある。

**`settle` を伸ばしても直るとは限らない。** ハンチングはリミットサイクルなので、
長い停留は**より多くの周期を平均するだけ**で振幅は消えない。`spread` の数値は
下がりうるが、平均は依然リミットサイクルの平均。

**したがって、摩擦の大きい関節では Breakaway map のほうが正しい道具**である。
Load map の本来の目的（負荷と釣り合い位置）については、
`peak static load 0.611 N·m` / `equilibrium +5.3884 rad` も同じ理由で疑わしい。

### Velocity sweep: 端のビンは信用してよいか

各計測脚は、**軸がまだ逆方向に動いている状態で**全速を指令して始まる（位置決め脚は
`position <= lo` になった瞬間に抜ける）。減速・停止・反転が終わるまでの標本は定常運動
ではない。

しかもこの過渡は**両脚で反対の端に落ちる** — `+` 脚は下端で反転し、`−` 脚は上端で
反転する。したがって最低ビンでは `+` 方向が過渡・`−` 方向が定常、最高ビンでは逆に
なる。半差は「過渡 − 定常」になるので**摩擦が低く出て**、半和には残差が残り、
**両端で符号が逆**になる。

**2026-08-07, RS-04 での実測**: 摩擦が中央 0.60 に対し端で 0.49 N·m まで下がり、
負荷曲線が −0.08 → +0.115 N·m の傾きを見せた。これは**ばね項に見えるが、ばねではない**。

`VelocitySweepSpec::lead_in_rad`（既定 = half_span の 15%）で各脚の最初の走行を
記録対象から外すことで解決した。判定は**位置**で行う — 一部ファームは velocity を
0 で返すので「速度に達したか」はフィードバックでは答えられない。

代償は端のカバレッジ。ただしそのビンは元々定常運動で測れていなかったので、失うのが
正しい。

### Velocity sweep: 速度が出ているか

`traversed_speed_rad_s`（位置差分から算出）が指令速度に近いかを見る。
**報告速度（`velocity_rad_per_s`）は信用しない** — RS-03 はほとんどのフレームで
velocity を厳密に 0 で返すため、報告値の平均は指令の 1/5 になる。
停止判定は位置で行っており、報告値が位置と矛盾したときだけ
`reported velocity` として表示される（そのときそれは関節ではなく**モーターの
フィードバックについての事実**）。

### `not at rest` は個体の問題ではなく、判定が信用できない量を見ている

**2026-08-07、RS-04 2 台でどちらも `5 of 5 not at rest`。** それ以前に
「id 3 だけ `no` なので機械的な振動が疑わしい」と書いたが、**その仮説は成り立たない**。

`rested` の判定は **`|velocity| ≤ 0.05 rad/s` が `rest_window_s`（既定 0.3 s）継続**
であり、**このファミリの速度フィールドは信用できないと §7 で文書化したもの**である。
Velocity sweep の停止判定は位置由来に直したが（`traversed_speed_rad_s`）、
**同じ理由がこの静止判定には適用されていない。**

観測とも整合する: RS-03 は velocity を厳密な 0 で返すので**判定が自明に通り**、
RS-04 はノイズが 0.05 rad/s を超えると**一度も通らない**。同じ機構で正反対の結果になる。

**別ベンダーとの比較が裏付けた（2026-08-08）**: 同じバス・同じ run で、
**MyActuator (RMD-X4) には注記が付かず、RobStride 3 台すべてに付いた**。
速度をまともに返すファミリでは判定が通り、返さないファミリでは通らない。
**モーターの機械的な問題ではなく、判定側の問題**である。

**2026-08-08 に修正済み。** 静止判定も位置由来になった — `rest_window` の間、
位置が `motion_threshold_rad` を超えて動かなければ静止とみなす。閾値は
「動き出した」判定と同じものを使うので、**「静止」と「運動」が 1 つの測定の裏表**に
なる（既定 0.3 s の窓で約 0.067 rad/s のドリフトを許容し、旧判定の 0.05 rad/s と
同程度。基準を黙って緩めてはいない）。

したがって**この節より前に取った `not at rest` 付きの測定値は、注記を無視してよい** —
判定が信用できない量を見ていた時期のものなので。

### Breakaway map: 全位置が破断したか

**破断しなかった位置は平均から除外される。** その除外は無作為ではない —
**負荷が助ける位置ほど破断しやすい**ので、残るのは楽な位置ばかりになり、
**平均は必ず低く偏る**。

**実測（2026-08-07, RS-03）**: ランプ上限 0.85 N·m では 5 位置中 4 位置しか破断せず
平均 **0.647 N·m**。同じ関節をランプ 3 N·m で測り直すと 5 位置すべて破断して
平均 **1.180 N·m** — **1.8 倍**。低い方の値も「測れた位置の平均」としては正しく、
だから間違いに見えない。

`POSITIONS` と、プロットの点の数を必ず突き合わせること。**両方向で 5 位置なら
青 5 点・橙 5 点**。片方が欠けていたら、その平均は使えない。

### 角度依存は「実際に動いた範囲」に対する値

**プロットの x 軸の幅を必ず見ること。** 指定した `half_span` の 2 倍とは限らない。

**2026-08-08, RMD-X4 (id 1)**: ±0.3 rad を指定したが、実際の点は **0.016 rad** にしか
広がらなかった（同じ設定で RS-03 / RS-04 は 0.55 rad 前後）。**この個体は位置間の
移動がまったく起きていない。** 未解決 — handover 参照。

> 同じ run を fine position 修正の前に取ったときは 0.12 rad に見えた。**その差は
> 実測の差ではなく、制御応答の位置が 1°/LSB に量子化されていたため。** 分解能を
> 上げたら見かけの広がりが 1/7 になった。**「広がっているように見える」ことが
> 分解能の産物でありうる**という例として残す。

測定自体は有効（5 位置・両方向すべて揃っている）だが、**`ANGLE DEPENDENCE 32%` は
0.6 rad ではなく 0.12 rad の範囲の値**であり、RobStride の 47% / 27% / 15% と
**同じ土俵では比較できない**。角度依存を機種間で比べるなら、まず span を揃えること。

### Breakaway: 天井に当たっていないか

「動き出さなかった」と「ランプが上限で終わった」は別。後者は
`not reached below X N·m` と報告される（`0 N·m` と出して摩擦ゼロに見せない）。

envelope のトルク上限に当たった場合は、GUI が **`Retry at X N·m`** ボタンを出す。
提示値は上限の 2 倍で、**測定値ではない** — ガードは上限を超えた瞬間に落ちるので、
記録された標本はどれも上限のすぐ上にあり、「あとどれだけ必要か」を語らない。
黙って上げずに 1 クリックにしてある。

## 7.5 測定データの保存先

すべての run は**自動で CSV に保存される**。既定は `<ホーム>/misa-actuator-data/`。

```
20260807-031308Z-breakaway-map-id96.csv
```

先頭に `#` メタデータ（run 名・motor id・標本数・画面に出た要約値）、続いて
`t_s,cmd,position_rad,velocity_rad_per_s,torque_nm,current_a,temperature_c`。

**保存先は `MISA_ACTUATOR_DATA_DIR` で変えられる。** GUI も CLI も同じ変数を見る。

```powershell
$env:MISA_ACTUATOR_DATA_DIR = "D:\campaign-2026-08"
```

設定項目ではなく環境変数にしてあるのは、アプリに設定を置く場所が無いため
（設定ファイルを持っていない）。起動ごとに忘れる入力欄は固定の既定値より悪い。

**なぜボタンではなく自動保存なのか。** 30 秒の run のデータを「Export を押し忘れた」で
失うと取り直しになり、複数台の一括測定では押す人がいない。そして実際、breakaway map の
結果が左右に分かれた原因は、画面の 4 点ではなく**保存された 3682 標本を 10 本のランプに
分解して初めて確定した**（§7 の実例）。
