## 2. 安全

**実機に触る前に読むこと。** 0.8 N·m から 400 N·m まである。

### `disable` は保持される安全状態ではない（DAMIAO で実測）

ベンチ §1:

> `disable` 直後に `mit --kp 5` を送ると **1.013 N·m を出力**した。次の制御フレームで
> 再励磁される。`status` も内部でゼロゲイン MIT フレームを送るため `err=Enabled` を
> 再表示する。**投入時から励磁状態でもあった。**

`Session` には停止手段が 3 系統ある（STOP フラグ / ウォッチドッグスレッド /
`Drop` でのワーカー join）が、**それはソフトウェアの停止経路の話**で、モータが
無励磁でラッチされることを意味しない。物理的に止めたいなら電源を切る。

### ホールディングブレーキ

`myactuator-cli brake` は**フラグ無しで解放する**（施錠は `--lock`）。
垂直軸に負荷が吊ってあれば落下する。

**解放前に無負荷を確認する手順**（実際に使った）:

```
myactuator-cli -i pcan:usb1@1M -m 1 brake        # 解放
myactuator-cli -i pcan:usb1@1M -m 1 status       # 数回繰り返す
```

位置が動かず、トルクがノイズ範囲（±0.1 N·m 程度）なら無負荷。ドリフトするなら
負荷が掛かっている。

**未確認**: 解放時に保持トルクがゼロなのか「最後に指令した値」なのかは調べていない。

### 非常停止は「全部」を止めなければならない（2026-08-05 に実機で踏んだ）

**右上の STOP が Multi タブのモータに届いていなかった。** 実機で RS-04 2 台を
駆動中に押して、**何も起きなかった**。緑のドットもそのまま、streaming も継続、
`starved` カウンタが増え続け、ログの件数も増えなかった（= 停止経路が走っていない）。

原因は配線漏れ 1 行:

- `ConnectionBar` の STOP は**画面上で最大・常に押せる非常停止として設計**されている
  （ファイル冒頭にそう書いてある）
- それが呼ぶ Tauri コマンド `stop` は `AppState.session`（**単体セッション**）しか
  見ていなかった。`AppState` にスロットを 2 つにしたときに、`multi` 側を足し忘れた
- **同じ経路に Esc とエラーバウンダリも乗っている。** つまり **UI がクラッシュしても
  Multi タブのモータは止まらなかった**

**修正**: `AppState::stop_all()` を作り、`stop` と `multi_stop` の**両方**がそれを
呼ぶ。名前は 2 つ残すが**挙動は同一**にした — 「どちらの stop を呼ぶか」を
呼び出し側に選ばせる構造そのものが事故の原因だったので、選べないようにするのが修正。
**セッションのスロットを増やすときは `stop_all` にも足すこと。**

**2026-08-06 に実機で確認済み。** しかも `safety.rs` へ統合した**あとの**コードで:
RS-03 を `slcan:COM11` で駆動中に右上 STOP を押し、ドットが灰色に戻り、ログに
`warn: stopped every motor (UserRequest)` が出た。**昨日はこの行が出なかった**
（`starved` だけが増え続けた）ので、**ログに 1 行出るかどうかが判定基準**になる。

**回帰テストがある**（`the_stop_reaches_a_multi_motor_session`）。**最初に書いた版は
バグを検出できていなかった** — ハートビートを打たないテストではウォッチドッグが
750 ms で止めるので、`stop_all` が何もしなくても通ってしまう。`connect_with(..., None)`
でウォッチドッグを切って初めて落ちるようになった。**停止のテストを書くときは、
ウォッチドッグで通っていないことを確かめること。**

**併せて直した非対称**: `open_elsewhere` は両方向のために書かれていたのに
**片方からしか呼ばれていなかった**。multi を開いた状態で単体接続すると、
「閉じてください」ではなく driver の奥で `PCAN_ERROR_NETINUSE` が出ていた。

### CLI は Session の安全網の外にいる

`robstride-cli enable` は **Drop での自動 disable を意図的に無効化する**:

```rust
// Caller likely wants the motor to stay enabled — leak the handle
// so Drop doesn't auto-disable.
std::mem::forget(motor);
```

ターミナルを閉じても通電したまま、ホスト側の監視はゼロ。診断作業（§8）は CLI で
行うので、これは日常的に踏む経路。

### 設定を壊す操作

### 安全エンベロープの実効性

`Characterize` は `SafetyLimits::gentle()`（1 N·m / 60 °C / ±0.5 rad / 30 s）で走る。
**この枠は思ったほど効かない。**

- **RS-04 の静摩擦分布の内側にある。** 実測 n=20 で mean 0.912、sd 0.118、
  **6/20 が 1.0 N·m を超える**。既定のまま実機 breakaway を回すと約 3 割が
  トルク上限で打ち切られ、検閲された値を返す
- **温度ガードは RS-04 で何もしない。** `torque_ok` / `temperature_ok` は
  非有限値を「範囲内」として通す（意図的な設計で理由もコメントにある）。
  ところが **RS-04 は `mit_control` 以外で温度もトルクも返さない**ので、
  quasi-static 経路ではガードが常に素通りする
- **`Chirp` にはエンベロープが無い。** `run_chirp_with` は `SafetyLimits` を取らない。
  duration と abort フラグだけ。トルクチャネルの chirp は振幅指定だけが安全装置

### 速度上限は目標値であって保証ではない

`hw_check_20260801_172404.log`: 速度上限 1.00 rad/s を指令して**ピーク 1.816 rad/s**
（+82%）。プロファイル生成器の目標であってクランプではない。

## 3. 構造と、そうした理由

**crate 一覧は README にある。** ここには設計判断だけ書く。

### 抽象は 2 層ある

- **`Actuator`**（`crates/misa-actuator/src/traits.rs`、16 メソッド。うち 5 つは
  既定実装 — `current_run_mode_hint` / `is_enabled_hint` / `scan_bus` /
  `probe_motor` / `read_parameters`）。GUI も TUI も sysid もこれしか見ない
- **ベンダーごとのバストレイト**（`RobstrideBus` / `DamiaoBus` / `MyActuatorBus` /
  `LkBus`）。ドライバをトランスポートに対してジェネリックにする。
  **`protocol` / `driver` / `cli` の三つ組がベンダーごとに存在する理由がこれ**

`Actuator` の拡張は**既定実装つきメソッド**で足す。そうしないと 4 ドライバ全部を
同時に触ることになる。

### 共有バスの宛先判定: 4 社を監査した結果（2026-08-05）

**1 本のバスに複数モータを載せると、「応答の取りこぼし」ではなく「他モータの値を
自分の値として受け入れる」経路が問題になる。** 4 社すべてを読んだ結果:

| ベンダー | 判定 | 内容 |
|---|---|---|
| **RobStride** | **バグだった → 修正済み** | `recv_status` がフレーム種別だけで受理し、**送信元モータ ID を見ていなかった**。同一バスの別モータのステータスを自分の位置として返す。送信元は `extra_data` の下位バイト（`device_id` は宛先ホスト）|
| **DAMIAO** | **プロトコルの制約** | フィードバックの ID は**4 bit しかない**（バイト 0 の上位は状態コード）。下位 4 bit が一致する ID は区別不能で、既定 `MST_ID = 0` は「どの応答者でも受理」。実装は正しく、**`build_multi` が曖昧な構成を起動前に拒否**する |
| **MyActuator** | **問題なし** | 応答 ID がモータ毎（`0x240 + id`）で、`send_recv` が `can_id` で弾き、**さらにコマンドのエコーバイトも検証**する |
| **LK Motor** | **問題なし。4 社中で最良** | 下記 |

**LK Motor が手本になっている。** RS485 は多ドロップなので同じ問題を持つはずだが:

- `recv_for(motor_id)` が `resp.motor_id` を**明示的に検証**する
- **他モータ宛を捨てるときに `warn` を出す**（無記録で捨てない）
- **`LkBus::transact` が「1 呼び出し = 1 トランザクション」**で、`Shared<B>` の実装が
  **送受信を 1 回のロックで囲む**

最後の点が重要で、**CAN 側に無い原子性を LK 側は持っている**。CAN のベンダーバストレイトは
`send` と `recv` が別呼び出しなので、`Shared` 越しでもロックが切れる（下記）。

**CAN 側を直すなら `LkBus` の形にすればよい** — 新しい設計を考える必要はなく、
同じリポジトリに動いている実例がある。

`[backend:]device[@bitrate[,data]][?opts]` で `can0` / `pcan:usb1@1M,5M` /
`slcan:COM5` を書き分ける。

**PCAN は `PCANBasic.dll` を実行時 `LoadLibrary` で読む。** リンク時依存にすると
PEAK ドライバの無いマシンで**起動すらできなくなる**。遅延ロードなので、アダプタが
無くてもアプリは立ち上がり、接続時に初めて明示的なエラーが出る。

### `misa-actuator-core`: セッションとワーカー

- **Setpoint は上書き、Command はキュー。** 位置スライダを動かすたびに指令が
  積み上がってはいけない。逆に Enable/Disable は取りこぼしてはいけない
- **ウォッチドッグは専用スレッド。** ジョブはワーカーのループを数十秒占有する。
  ループ内チェックでは**まさに一番危険な時間帯に動かない**
- **テレメトリだけ別チャネルで落としてよい。** UI が遅れたらプロットのサンプルは
  捨てる。状態変化とエラーは捨てない

### 1 バスに複数モータ: `multi.rs` と `multi_session.rs`（2026-08-05 追加）

**`misa-actuator-core` に置いた。GUI ではない。** 同じものが TUI と CLI からも
要る（`misa-actuator-monitor` は §7 の未実装案件そのもの）し、シミュレータ相手の
テストが GUI をビルドせずに書けるのが決め手。**既存の `Session` は 1 行も
変えていない** — 1 台なら従来経路、複数なら `MultiSession`、選ぶのは呼び出し側。

**メッセージブローカーは作らなかった。** 一度は設計したが、必要なのは
「他モータ宛のフレームを配り分ける」ことではなく「**前のターンの残骸を、次の
ターンの答えと間違えないこと**」だった。フィードバックフレームにシーケンス番号は
無いので、取り違えは黙って古い位置を返す。実装は `SharedCanBus::drain_stale()`
（タイムアウト 0 で最大 64 フレーム捨て、**捨てた数を返す**）1 個で足りる。
ルータを足せば、各ドライバの受信ループを全部書き換える必要があった。

**`SharedCanBus` は `misa_can::CanBus` を実装する newtype。**
`Arc<Mutex<Box<dyn CanBus>>>` を包んで `CanBus` を実装しているので、
**各社のアダプタは無改造で受け取れる**（`Shared<B>` を各社の bus トレイトに
実装すると孤児則に触るが、こちらは `misa-can` のトレイトなので触らない）。

**ワーカーは 1 本、パスには予算がある。** `Worker::pass()` は全モータを 1 巡する
が、**与えられるのは tick 1 周期分だけ**。予算が切れたら残りは飛ばし、
**次パスで先頭に回す**（`next_start`）。理由は実測にある: 1 トランザクションは
バスのタイムアウト全部を使い得るので（DAMIAO の欠落で 2026-08-03 に見た）、
予算が無いと**遅い 1 台が全員のレートを決める**。飛ばした回数は `starved` として
スナップショットに出る — 0 でなければ、レートを決めているのは設定した tick では
なくワイヤ。**予算が縛るのは「何台が遅れるか」で、「1 回がどれだけ掛かるか」では
ない**（タイムアウトは共有トランスポートの持ち物なので、1 周期の超過は起こり得る。
モータ毎のタイムアウトはトランスポート側の変更が要る）。

**1 台の故障で 3 台を落とさない。** 連続失敗 `CONSECUTIVE_FAULT_LIMIT = 20` で
そのモータだけ放置する。`disable_all()` は**失敗しても次のモータに進む** —
途中で `?` すると、最初の 1 台が応答しないだけで残りが通電したままになる。

**スナップショットの深さは 2**（単体 Session は 4）。プロットが無いので、
古い読み値には価値が無い。

**設定の検証を先にやる。** `check_spec` と `check_damiao_addressing`。後者は
DAMIAO の 4 bit id 制約（§3 の宛先判定）を**接続前に**弾くためのもの。

**スキャンは通電するものを最後に回す。** `SCANNABLE` の順は
Sim → Robstride → Myactuator → **Damiao**。DAMIAO にはブロードキャスト ping が
無く、探索が enable → listen → disable になる（`probe_energises_motor` が
true を返す唯一の社）。**シミュレータもスキャン対象に入れた** — 接続フローが
「スキャンで見つけたモータ」しか受け付けないので、入れないと**実機を通電させない
限り Multi タブを 1 度も動かせない**。

### `misa-actuator-sim`

`bench-measurements-2026-07-30.md` の実測値からプリセットを作ってある

#### 接続フロー: Scan は Connect より先（2026-08-06 に直した）

**以前は循環していた。** Connect には MOTOR ID が必要で、ID を知るには Scan、
Scan には Connect が必要（`ConsoleTab` の Scan が `disabled={!connected}`）。
**id 96 の RS-03 は既定の id 1 で connect が失敗するので、GUI から到達不可能だった。**

**現在**: Scan は接続状態に応じて経路を変える。

| 状態 | 経路 |
|---|---|
| 未接続 | **自分でバスを開いて probe して閉じる**（`multi_scan`、Multi タブと同じ）。model も id も不要 |
| 接続中 | セッションがチャネルを所有しているのでワーカー経由（従来） |

**両方要るのは 1 チャネルの所有者が 1 つだから。** 未接続用の実装は Multi タブの
ために書かれていて、**問題が起きるタブに提供されていなかっただけ**だった。

**見つかった行はクリックできて、MOTOR ID と MODEL の両方が埋まる。** probe は
どうせ identity を読むので、推測が必要だった 2 つのフィールドこそスキャンが答えを
持っている。

**共有している状態**（`App` の `ConnectionForm` と `ScanRange`）:
driver / interface / bus / motorId / model / スキャンレンジ / スキャン結果。
**INTERFACE はバーと Multi タブで二重に入力させていた** — バスは 1 つで、
チャネルの所有者も 1 つなので、別の値にしても意味が無い。
**タブを切り替えても発見結果は残る**（機械についての事実であって、タブの持ち物ではない）。

#### Multi タブ（2026-08-05 追加）

`ui/src/components/MultiTab.tsx`。スキャン → 選択 → 接続 → 一括 Enable/Disable →
モータ毎の目標値 → 表で監視。**プロットは意図的に入れていない**（4 台同時に見る
のが目的で、50 Hz × 4 のプロットは得られるものに対して高すぎる）。

- **`AppState` には Session のスロットが 2 つある**（`session` と `multi`）。
  **1 CAN チャネルの所有者は 1 つ**なので、片方が開いていれば他方は
  `PCAN_ERROR_NETINUSE` になる。タブは上のバーを使わず自分で接続し、
  単体セッションが開いていればそう言う（`open_elsewhere`）
- **報告されなかった量は `null` で来て em ダッシュで出す。0 にしない。**
  温度を返さないドライバが複数ある（§4）。`multi_session.rs` の
  wire-format テストが `"temperatureC":null` を固定している
- **各行に測定からの経過（`age_ms`）を出し、500 ms を超えた行は薄くする。**
  共有ワイヤではモータがターンを飛ばされ得るので、いつ測ったかは測定値の一部。
  初回応答前は 0 ではなく「never」
- **通電の警告は決める場所に置く。** DAMIAO のチェックボックスに `ENERGISES` の
  タグ、その社を選んでいる間だけ理由付きの 1 行が出る。外すと消える
- **目標値は streaming 中しか送られない。** idle では表の TARGET 欄に入力しても
  何も起きず、理由は脚注にしか書いていなかった（Console はボタンが入力欄のすぐ下に
  あるが、Multi は表の中と上部で離れている）。**2026-08-06 に実際に迷わせたので**、
  idle で目標値が選ばれている間は `targets are not being sent — press Start streaming`
  と「idle」の隣に出すようにした
- **レートは streaming 中しか出さない。** `achieved_rate_hz` は**ループの**レートで、
  パスが実際に交換するのは駆動中のモータだけ。idle では 200 Hz と出るが実際の
  読み出しは 50 ms 毎（20 Hz）なので**10 倍の過大表示**になる。**2026-08-05 に
  リリースビルドのスクリーンショットで見つけた** — 同じ画面の `AGE` 列が 14〜19 ms
  で、表示と矛盾していた。Console タブは元から
  `idle (polling at 20 Hz)` と出し分けていたので、そちらに合わせた
  （[ConsoleTab.tsx:226-227](../ui/src/components/ConsoleTab.tsx#L226-L227)）

- **目標値の欄はワーカーが保持している値で埋める。0 で初期化しない。** これが無いと
  接続直後の欄が 0 になり、**Start streaming で全軸が原点へ飛ぶ**。§4 参照 —
  シミュレータでは原理的に見つからない欠陥だった

## 4. 実機でしか分からなかったこと

**ここが最大の資産。** モータが無いと再取得できない。
**数値の一次資料は [`bench-measurements-2026-07-30.md`](bench-measurements-2026-07-30.md)。**

### 1 バスに 2 台: 実機で確認したこと（2026-08-05、RS-04 ×2、pcan:usb1、classic 1 Mbps）

**構成**: id 2（`0.4.1.32`）と id 3（`0.4.1.35`）。**どちらも RS-04**。同一機種なので
フィードバックフレームの構造が同じで、**宛先の取り違えが最も起きにくく気付かれない
条件**。無負荷、軸フリー。

**1. 宛先判定は効いている。** 両方 disable のまま片方の軸を手で回した:

| | 回す前 | 回した後 |
|---|---|---|
| id 2 角度 | 1.260 | **0.596** |
| id 3 角度 | 2.189 | **2.189**（不変） |
| id 3 目標値 | 2.189058 | **2.189058**（ビット一致） |

**通電せずにできるテスト**である点が重要。読み取り経路（`recv_status`）が修正箇所
なので、Enable は要らない。**ただしこれは「返信が正しいモータに帰属している」
確認であって、修正前のコードがここで失敗する確認ではない**（`dea7d0f^` で再現は
していない）。

**2. 指令もモータ毎に分かれている。** streaming 中に id 3 の目標値だけ +0.1 rad:
id 3 が 2.190 → **2.290**（目標 +0.1006）、id 2 は 0.598 → 0.606。
漏れていれば id 2 の行に 2.29 が入る。入っていない。

**3. レートはワイヤが決める。実測 145〜154 Hz / 台。** tick は 200 Hz で、
`starved`（予算切れパス）が常時増える。**2 台でこれなので 4 台なら更に落ちる。**
設定値ではなく `achieved_rate_hz` を見ること。

**4. 駆動中は温度が取れない。** idle では 29.0 / 30.0 ℃ を出していた 2 台が、
position モードで streaming すると両方 `—` になる。§4 の「RobStride は MIT 以外で
温度を返さない」と整合。**古い値を出し続けずに「報告なし」に落ちるのが期待動作。**
**2026-08-06 に RS-03 でも同じ**（接続直後 27.0 ℃ → 駆動後 `—`）。機種差ではなく
RobStride の性質。

**5. 未タッチのモータは「柔らかい保持」になる。** 目標値を一度も触っていない
モータは毎パス「測定値を目標値にする」が続くので、**自分の軸に追従し続ける**。
手で回しても跳ね戻らない代わりに、**負荷が掛かっていればゆっくり流れる**
（実測で 5 秒に 0.008 rad）。単体ワーカーと同じ設計で、意図的。
**逆らわせたいなら目標値を一度入力する** — その時点でシードは止まる。

### 1 機種だけでは見つからないバグがある

ベンチ §7.5 の教訓。**このプロジェクトで最も転用価値が高い。**

`Actuator::set_torque` が RobStride で **N·m ではなくアンペアを送っていた**
（Kt = 1.5093 倍の誤り）。核心トレイトの静かなスケーリング事故で、
**2 機種の推定値が食い違ったから見つかった**。1 機種なら両方見逃していた。

### RobStride: 機種はファームウェアのバージョンで分かる（確信度に注意）

**マイナー成分が機種番号、メジャーが製品ライン**（`0` = RS、`10` = EduLite）。
実機 RS-04 は `0.4.1.32`、**RS-03 は `0.3.1.21`**、EduLite05 は `10.5.0.1`。

**2026-08-06 に RS-03 で 3 機種目の裏付けが取れた。** マイナー 3 → RS-03 と判別され、
同時に読んだ `limit_torque = 60 N·m` が
[`param-table-firmware-divergence.md`](../crates/robstride-protocol/doc/param-table-firmware-divergence.md)
の「RS-03/06 は 60」という記述と一致した — **バージョンとトルク上限という 2 つの
独立チャネルが同じ機種を指した**（下記の突き合わせ機構が実際に効いている例）。

**証拠の内訳を正確に**:

- **強い**: motorstudio の "Detection Devices" が**バス上に GetDeviceId と
  バージョン読みしか流さない**ことをキャプチャで確認済み。パラメータ読みは無い。
  この消去法が結論を許している
- **弱い**: 公式リリース資産 7 件のファイル名は**ベンダーが付けた名前**であって
  測定ではない。機種ごとに `0.N.x.y` で切っていれば定義上そうなる
- **n = 2 / RS 系、1 / EduLite 系**（RS-04 と RS-03、EduLite05）。
  **RS 系で 2 機種が別のマイナーを積んでいる**ことが確認できたので、
  「マイナー = 機種番号」の根拠は 1 機種のときより強い
- **「メジャー = ライン」は 1 バイト × 1 台。** しかもベンダー自身の
  `AppCodeVersion` 文字列は `1.0.5.0.1` と**5 成分**で、`0x0A` を「10」と
  レンダリングしていない。先頭バイトが 2 成分を詰めている読み方も同じくらい整合する
  （その場合も機種桁は byte[1] なので結論は生き残るが、「メジャー = ライン」は残らない）

**反証されうる条件**: EL01/02/04 のメジャーが 10 でない / RS 系のメジャーが
バンプされる / EduLite05 が `0.5.x.x` を積む / RS-07 以降が出る。
**ヘッドルームはゼロ**で、ベンダーがメジャーを一度上げただけで対応表は壊れる。
未知のメジャーでは `None` を返すので、誤判定ではなく判定不能になる（フェイルセーフ）。

`limit_torque = 115` は独立した第 2 の判別チャネル。**2026-08-02 に突き合わせを実装した**
（`misa-actuator-core/src/factory.rs` の `robstride_named_identity`）。

バージョンが機種を名指しできた場合も `limit_torque` / `limit_spd` を読み、
**名指しされた機種の MIT レンジで表現できない値なら「2 つのチャネルが食い違っている」
と警告する。** これは上記のヘッドルーム ゼロ問題に対する唯一の検出手段で、
**操作者の `--model` 選択がバージョンと一致していても発火する**
（両方間違っている可能性があるものの一致は根拠にならない）。

制約 3 点:

- **反証のみ。** `consistent_with` は「レンジで表現できない」ことしか言えない。
  一致は「矛盾が見つからなかった」であって同定ではない
- **無応答は矛盾ではない。** パラメータ読みが返らなければ警告しない
- **接続ごとにレジスタ読み 2 回増える。** 従来はバージョンで確定した時点で
  早期 return していた。フォールバック経路が既に使う文書化済みの読みなので
  新たな危険は無いが、往復は増える

### RobStride: 行き止まりだった経路

同じ調査を繰り返さないこと。

| 経路 | 結果 |
|---|---|
| `0x0000 Name` | RS-04 / EL05 とも全 FF（工場未書き込み） |
| `0x0001 BarCode` | 同上 |
| `0x1007 AppCodeName` | EL05 は `EL_motor`、**RS-04 は `motor`** で判別不能 |
| comm type 0 | MCU UID のみ |
| バージョン応答 Byte7 | **両機種とも `0x07`** — モデルコードではない |

Byte7 の否定は強い証拠。**MIT スケールが 21.8 倍違う 2 台が同じ値を返した。**

### RobStride: バージョン読み出しの罠

マニュアルの「コピペミスに見える記述」が**両方とも正しかった**:

```
要求  ID=0x0400FD01  data=00 C4 00 00 00 00 00 00
応答  ID=0x020001FD  data=00 C4 56 00 04 01 20 07   → 0.4.1.32
```

- **要求の comm type 欄は `4`** — `DISABLE` と同じ値。`00 C4` でしか区別できない
- **応答は comm type `2`** — 通常フィードバックと同じ。`00 C4 56` でしか区別できない

**応答をフィードバックとしてデコードすると、それらしい数値のゴミになる。**

### RobStride RS-04: この個体の癖

| | |
|---|---|
| firmware | 0.4.1.32 |
| MCU UID | `0F302000C03B5CC3`（受信バイト列の**逆順**が motorstudio 表示） |
| `limit_torque` (0x700B) | **115 N·m** — family 中 RS-04 でしか表現できず、単独で一意特定できる |
| `limit_spd` (0x7017) | **1 rad/s** — 保存値であって能力ではない。ドライバが Position モード投入前に既定 5.0 で**上書きする** |
| **`MeasuredTorque` (0x302C)** | **常に 0**。3 run / 72 サンプルで非ゼロゼロ件。MIT では 109/109 非ゼロ |
| 温度 | `mit_control` 以外では NaN |
| `loc_kp` | 80。約 0.9 N·m の摩擦に対して弱く、load-map が**ハンチングする** |
| Kt（実測） | **1.5093** |

**`MeasuredTorque` = 0 の影響**: Position/Torque モードのフィードバックがこれを
使うので、`characterize load-map` が何も測れず、安全エンベロープのトルク上限も
検査対象を失う。回避は `--kt 1.5093`（`IqFilt` から `torque = current × Kt` を合成）。
なお `--report-current` は**ループレートを半減させる**ので chirp には向かない。

**熱特性はリーシュでは構造的に測れない**（ベンチ §4）。軸が
`err = −tau_ff/kp` で釣り合うため、指令 2.0 N·m に対し実測 0.141〜0.251 N·m
（伝達率 13%）。治具が要る。

### DAMIAO CAN-FD: レジスタ読みの欠落（**2026-08-03 に切り分け完了**）

**結論: モータは要求を受信して ACK し、そのうえで答えていない。取りこぼしは
CAN 層より上、ファームウェアである。** ホスト側・バス側は無罪。

#### 決定打（listen-only の 2ch キャプチャ）

PCAN-USB の 2ch 目を **listen-only**（送信せず、**ACK もしない**）で同じバスに繋ぎ、
1ch 目から読み出しながら観測した。失敗した読み出しについて:

- **要求フレームはバス上に出ている**（`0x7FF` の `READ motor 16 RID n`）
- **各要求は 1 回だけで再送が無い。** CAN は受信ノードが 1 つも無ければ ACK が
  返らず送信側が自動再送する。監視側は ACK しないので、**ACK したのはモータ**
- そのうえで **199 ms 待って応答が 1 本も出ていない**

**listen-only が必須である理由**: 通常モードの 2 本目を足すと、**モータが取りこぼした
フレームを監視側が代わりに ACK してしまう**。上の推論の足場がそれで消える。
非 PCAN バックエンドは listen-only を実装できないので `misa-can` が拒否する。

#### 測定値（`--read-attempts 1`、38 レジスタ/パス、2026-08-03）

| 条件 | 無応答 |
|---|---|
| 読み出し間隔 0 ms | 31/190 |
| 読み出し間隔 5 ms | 30/190 |
| 読み出し間隔 20 ms | 29/190 |
| タイムアウト 100 → 1000 ms | 8/38（遅れて届いたものは 0） |
| 要求を classic フレームで送信 | 6/38 |

**合計 109/684 = 15.9%**、どのノブにも動かない。旧記述の「11〜15%、n 未記録」を
これで置き換える。

#### 排除された仮説（4 つとも）

| 仮説 | 排除の根拠 |
|---|---|
| ホスト RX キュー溢れ | `PCAN_ERROR_QOVERRUN` を監視 → 全 run で 0 件 |
| リクエスト過密 | 間隔を 20 倍にしても率が変わらない |
| 応答が RID 不一致で捨てられていた | `recv_reg_reply` が破棄を計数 → 失敗時の破棄 0 件 |
| データフェーズ 5 Mbps の信号品質 | classic フレーム（全体 1 Mbps）でも同率。かつ破損は CAN が自動再送するので「遅延」になり「消失」にならない（1000 ms で不変） |

#### 旧記述の誤りを 2 つ訂正した

- **「ランダムなレジスタ」は誤り。** 読み出し順で**周期 ≈ 11**、多くは 2 つ離れた
  2 連発、位相は run ごとに変化。全 run で再現。しかも**周期は時間ではなく
  読み出し回数で刻まれる**（失敗はタイムアウト分の時間を食うので、20 ms 間隔を
  入れると run の実時間はほぼ倍になるが件数は変わらない）
- **「バスエラー無しだから破損していない」は成り立たない。** CLI は起動ごとに
  チャネルを初期化し直し、1 run は 38 読み出し（≈76 フレーム）しかないので、
  16% 破損してもエラーカウンタは警告閾値 96 に届かない。破損を否定するのは
  1000 ms の結果であって、警告が出ないことではない

#### 残っている未解明（**こちらの配線が原因の可能性あり**）

キャプチャの**応答側だけ**が不整合で、ここからは何も結論していない。

- **監視が、ホストは受け取った応答を見落としている**（overrun 0 件なのに）
- **同一応答が 4 回写る**ことがある。ハードウェアタイムスタンプで 0.4〜8.6 ms
  間隔で、CAN の自動再送（µs オーダー）では説明できない

要求側は完全に取れているのに応答側だけ落ちる非対称。**2 本目を足したことで終端が
3 個以上になっている可能性を先に潰すこと**（監視を外して欠落率が 16% に戻るかを見る）。

- ~~読み取り専用のはずの `info` が終了時に disable を送っている経路が未特定~~
  **解決。`DamiaoMotor` の `Drop` 実装**（`damiao-driver/src/driver.rs` 末尾）が
  ハンドル破棄時に disable を送っている。意図的な設計で、コメントにも
  「これは *この handle が指令をやめて de-energise する* 保証であって、
  モータが不活性になった保証ではない」と書かれている。
  **調査中に「`Drop` は無い」と誤って断定した** — grep の出力が件数上限で
  切れていたのを見落としたため。**打ち切られた grep から不在を結論しないこと。**

#### 再送は外せない

「欠落ゼロなら再送は不要」という分岐は成立しなかった。`--read-attempts 1` で 16%
落ちるので、**再送（3 回 + 5 ms）は実際に効いている** — 0.16³ ≈ 0.4% まで潰している。
`ReadOutcome` の修正（スキップを「キューが空」と報告していたバグ）は症状と一致して
いたが、**単独の原因ではなかった**。

**制御ループ側は今も落ちている**: FD で 48 リード中 8 件（16.7%）が無応答。
制御経路は再送しない（許容して継続する設計、§6）。

## 5. 直したバグ（再発しやすいもの）

### 台ごとの属性を 1 つに潰す（2026-08-07、同じ間違いを 3 回）

**一括測定で「台ごとの値」を「バッチ全体の値」に潰す間違いを 3 回繰り返した。**
毎回、症状はもっともらしい数値が出ることで、失敗として現れない。

1. **モデル** — スキャンが `RS-04` と識別しているのに、接続はバーの MODEL を全台に
   使っていた。バーが RS-00 のまま RS-04 を 2 台測り、**Kt が 0.2442 / 0.2035**
   と出た（正しくは 1.52 / 1.60）。MIT 量子化レンジが 17 対 120 なので**全部 7 倍
   ずれる**。比が 6.2 / 7.9 / 7.4 と 120/17 = 7.06 付近に揃うのが決め手だった
2. **Kt** — 個体差が 5% ある（RS-04 の 2 台で 1.5178 / 1.6006）。台ごとに測る既定に
3. **トルク天井** — バーの MODEL から導いていた。しかも最初の修正案が
   **「選択した中の最小値を使う」**で、これが罠。RS-05（0.55）と RS-04（12）が同じ
   バスにいたら両方 0.55 になり、**RS-04 は一切動かない**。安全上の問題を、全台での
   静かな測定失敗に置き換えるだけ

**教訓**: バスに載っているものは 1 種類とは限らない。**台に属する値は台に持たせる**。
「安全側に倒す」つもりの最小値は、測定を殺すことがある。

### 上限どうしをぶつける（2026-08-07）

ランプ上限（`max_torque_nm`）と安全 envelope（`τ limit`）を同じ値にすると、
**安全側が先に発火する**。判定は**実測**トルクで、電流由来のトルクは ±0.05 N·m の
ノイズを持つため、破断しなかったランプが自分の上限に届く直前に毎回中断される。
本来「上限まで上げても動かなかった」という**有効な測定結果**が、異常として捨てられる。

→ ランプ上限は τ limit の**半分**を既定にし、追従させた。バッチでも台ごとに
`clamp_ramp` で切り下げる。「どの run も収まれない天井は何も守らない」（§2）の
鏡像で、**通常運転で必ず触れる天井も余裕ではない**。

### 注記を数値から引き離す（2026-08-07）

`rested`（ランプ開始前に軸が静止していたか）は run が判定してタイルに出していたが、
**バッチの一覧は先頭の要約項目しか引用しない**。結果、前提が崩れた 0.669 N·m が、
健全な測定と同じ形で並んだ。→ 注記を数値の文字列そのものに載せた
（`0.669 N·m (not at rest)`）。**注記は、それが修飾する数値と一緒に動かないと届かない。**

### Windows 固有

**clap のスタックオーバーフロー。** Windows のメインスレッドスタックは 1 MB
（Linux は 8 MB）。clap derive は全サブコマンドの構築を 1 つの関数に展開するので、
`robstride-cli --help` が `main` の 1 行目に入る前に落ちた。
→ `.cargo/config.toml` で `/STACK:8388608`。

**タイマ分解能。** Windows の sleep は既定で ~15.6 ms（1/64 秒）に丸められる。
→ `misa-actuator::realtime` で `timeBeginPeriod(1)` と絶対デッドライン。

### スケーリング

**`Actuator::set_torque` が RobStride でアンペアを送っていた**（上記 §4）。

**`--model` の既定が `Edulite05` だった。** 「未指定」と「EduLite05 を選んだ」が
同じ文字列で区別できず、RS-04 に対して黙って RS-05 のスケール（21.8 倍差）で
動いていた。→ `MODEL_UNSPECIFIED = ""`。RobStride は未指定を拒否する。

**`from_gear_ratio` が P 版を無条件スキップしていた。** `DM6248P` と `DM10422P` は
P 版しか存在しないので識別不能になっていた。実機は DM4310 なので気づけず、
全機種網羅テストが捕まえた。

### 配線契約

**`rename_all_fields` の付け忘れ。** serde の `rename_all` は**バリアント名しか**
変えない。付け忘れると `timeout_ms` が snake_case で出てフロントで `undefined` に
なる — パースエラーではなく黙って壊れる。**黒画面を 2 回起こしている。**

`protocol.rs` のテストが配線契約を押さえている。**バグった期待値を固定しないこと**
（一度やった: `"timeout_ms":50` をテストに書いてバグを仕様化していた）。

`multi_session.rs` にも同じテストがある。そちらは**非有限値も固定している** —
`NaN` は JSON リテラルが無く serde は `null` を書くので、UI は「未報告」として描く
必要がある。ここが `0` に化けると、**無かった測定が妥当な測定に見える**。

### 宛先判定（複数モータで初めて出る）

**RobStride の `recv_status` が送信元モータ ID を見ていなかった。** フレーム種別
（`OperationStatus` / `FaultReport`）だけで受理していたので、**同一バスの別モータの
ステータスを自分の位置として返す**。送信元は CAN ID の `extra_data` 下位バイトに
入っているのに使っていなかった（`device_id` は宛先ホストであって送信元ではない）。

**モータが 1 台しか繋がっていない限り無害**で、複数モータ対応をやった瞬間に
バグになった類。§3 に 4 社の監査結果がある。

### 受信経路

**`try_read` がスキップを「キューが空」と報告していた。** エラー/ステータス/RTR を
弾いたとき `Ok(None)` を返すと、呼び出し側は自動リセットイベントを待ちに入る。
**目的のフレームが既にキューにあっても再発火しない。**
→ `ReadOutcome::{Frame, Empty, Skipped}` に分離。

**制御ループが 1 回の欠落で中断していた。** DAMIAO FD で 1/7 落ちるので 1 秒の
保持すら完走しない。しかも**指令は効いていてモータは動いていた**のに「応答なし」に
見えた。→ 連続 5 回まで許容、欠落数を必ず報告。

### GUI レイアウト

**`.app` が行数固定のグリッドだった。** バナー 2 つが条件付きなので子要素が 3〜5 個に
変動し、バナーが無いと `main` が `auto` 行に落ちる。
**全タブのプロットが content 高さに潰れていた。**

**uPlot がホストの `clientHeight` をそのまま使う。** 制約が無いと canvas が
8504px になる。凡例はホスト内・canvas の下なので、全高を渡すと次の要素と重なる。

**回転した 1 文字の軸ラベルは読めない。** `V` が `<` に見えた。

### シミュレータ

**制御則が呼び出しごとに 1 回しか評価されていなかった。** 速度制御が 27 rad/s に
発散した。→ プラントのサブステップ（2 kHz）で毎回評価。

  `embedBootstrapper`（+150 MB）

### PCAN のチャネル列挙: 使える問い合わせと使えない問い合わせ（2026-08-05 実測）

`interfaces` / GUI のドロップダウンの実装で分かったこと。**PEAK 2 チャネル接続状態で
実測**した。

| 問い合わせ | 結果 |
|---|---|
| `PCAN_CHANNEL_CONDITION`（`0x0B`、チャネル単位） | **全滅**。32 回すべて `0x00001C00`（ILLHANDLE） |
| `PCAN_ATTACHED_CHANNELS_COUNT`（`0x2A`、`PCAN_NONEBUS`） | **OK**。未接続 0、接続後 2 |
| `PCAN_ATTACHED_CHANNELS`（`0x2B`、構造体配列） | **OK** |

**チャネル単位の condition が「一番素直な方法」に見えるが動かない。** 台数を先に
訊いて配列で取る経路を使うこと。`CAN_GetValue` は optional シンボルで解決している
（古い DLL でも起動する）。

`TPCANChannelInformation` のレイアウトはヘッダからの転記＝推測なので、
**ハンドルが既知ファミリの範囲外なら結果全体を捨てる**チェックを入れてある。
別ドライバでレイアウトが違えば「不完全なリスト」ではなく「リスト無し＋警告」になる。
この個体では**ハンドル `0x0051`/`0x0052`・機種名 `"PCAN-USB Pro FD"`・condition 1 の
3 つが同時に整合**したのでレイアウトは確認済み。

**台数と命名できた数を突き合わせて、足りなければ警告する。** これが上記の
ILLHANDLE を見つけた仕掛け。空リストが「無い」なのか「訊けなかった」なのかを
区別できないと、列挙は嘘をつく。

### USB-CAN ドングルは「USB-CAN」と書いてあっても中身が違う（2026-08-05）

**同じ見た目の筐体で少なくとも 3 プロトコルある。** 手元の Seeed「USB-CAN Analyzer
V7.00」で踏んだ。

| プロトコル | prefix | 判別 |
|---|---|---|
| Lawicel ASCII（slcan ファーム: CANable / USBtin） | `slcan:` | `V`+CR に ASCII で答える |
| USB-CAN Analyzer の 20 バイトバイナリ | `usbcan:` | `V`+CR に**何も答えない** |
| RobStride 純正（`41 54` … `0D 0A`） | 未対応 | `rs04_manual_en.md:234` |

**判別方法**: COM ポートに `V`+CR を送る。手元の個体は
**1228800 / 2000000 / 115200 / 38400 / 9600 の 5 種すべてで 0 バイト**、
同期 CR 付き・小文字 `v`・`C`→`S8`→`V` も全滅だったので SLCAN ではないと確定した。
`VID_1A86 PID_7523`（CH340）は**素の USB シリアル変換なので、これだけでは
プロトコルは決まらない**。

**資料が 2 つあり、食い違う。食い違ったら動くコードを採る。**

| 資料 | 性質 |
|---|---|
| ベンダーのメモ | 20 バイト固定フォーマットと「チェックサム???」 |
| `canusb.c`（Linux 実装、MIT） | **実機で動いたコード** |

**どちらもリポジトリに入っていない**（一部ライセンス不明のため意図的に除外、
`.gitignore` に `/crates/misa-can/ref/`）。したがって**プロトコルの全体は
`misa-can/src/backend/usbcan.rs` のモジュールドキュメントに書き出してある** —
参照先ではなく、そこが記録そのもの。**このバックエンドの保守に必要なものを
`ref/` にしか無い状態にしないこと。**

**メモの「20 バイト送受信データ」は実際には設定コマンド**（`AA 55 12 …`）で、
**データフレームは可変長**だった。メモだけで実装すると全滅する。

```
データ: AA | 11ERLLLL | ID(LSB 先、標準 2 / 拡張 4 バイト) | データ×DLC | 55
        E=拡張, R=リモート, LLLL=DLC。チェックサムは無く、末尾 0x55 が終端
設定  : AA 55 12 speed frametype filter[4] mask[4] mode 01 00 00 00 00 checksum
        checksum = byte 2〜18 の総和の下位バイト（メモの「蓄積」はこちらの話だった）
```

**リファレンス実装にバグがある。** `frame_is_complete` が**拡張フレームでも `DLC+5`**
としているので（送信側は 4 バイト書いているのに）、2 バイト早く「完了」と判断して
ストリームがずれる。
**RobStride は 29 bit ID なのでこれは即座に踏む。** こちらの実装はフレーム種別ごとに
長さを数え、**末尾 0x55 も検査**するので、長さの間違いは「破棄」になって
「壊れた読み値」にはならない。

**`usbcan:` バックエンドでできること・できないこと**（`misa-can/src/backend/usbcan.rs`）:

- **ビットレートは設定できる。** 5k / 10k / 20k / 50k / 100k / 125k / 200k / 250k /
  400k / 500k / 800k / 1M の 12 段。範囲外は一覧つきで拒否
- **サイレントモードがあるので listen-only が使える**（PCAN 以外で唯一）
- **オーバーラン数もハードウェアタイムスタンプも無い。** DAMIAO の FD 欠落を
  切り分けたのはその 2 つ（§4）なので、**診断用途には PCAN を使うこと**。classic 専用
- **シリアルのフレーミングで資料が食い違う。** `canusb.c` は **2 Mbaud / 2 stop bits**
  （`CSTOPB`）、メモは 1,228,800 / 1 stop bit。**既定は動くコード側**にして、
  `?serial-baud=` と `?stop-bits=` で切り替えられるようにした。
  **アダプタは設定コマンドに応答を返さないので、フレーミングを間違えても
  エラーにならず「受信 0」になるだけ** — 何も受信しないときはここを最初に疑う
- **`COM1` のような素のポート名は今も `slcan:` 扱い。** ポート名から 2 つを
  区別する手段が無く、推論を変えると既存のコマンドラインが壊れるため、
  `usbcan:` は明示指定

#### 実機で動いた（2026-08-05）。ただし落とし穴が 2 件

RS-04（id 2）に対して `scan` と `identify` が通り、**PCAN と同一の結果**を返す。
シリアルは **2 Mbaud / 2 stop bits が正解**（リファレンス側）で、ベンダーメモの
1,228,800 / 1 stop bit ではない。設定コマンドも効いている（1 Mbit/s でなければ
バス上のフレームを復号できない）。

**落とし穴 1: 設定コマンドの直後は送信できない。** アダプタは設定を受け取ると CAN
コントローラを再初期化し、**その間に渡したフレームを捨てる**。100 ms の settle を
入れるまで、**最初の 1〜2 フレームが消えていた**。

証拠の出方が分かりにくいので記録しておく:

| 送った probe | PCAN が聞いた |
|---|---|
| id 1,2,3,4 | **3,4 のみ**（最初の 2 つが消えた） |
| id 2 だけ（= 最初の 1 つ） | **0 フレーム** |

**リファレンス実装では表に出ないバグ**。あちらは設定を送ったあと受信専用モードに
入るので、失われた最初の送信に気付く機会が無い。

**落とし穴 2: このプロトコルには ACK が無い。** 設定コマンドにも応答が返らないので、
**アダプタがこちらのバイトを理解したという確認が原理的に取れない**。シリアル設定を
間違えても、配線が悪くても、個体が壊れていても、症状は同じ「沈黙」。
**切り分けは必ず PCAN を並べて行うこと**（片方で送って他方で聞く）。

**配線不良で 1 時間使った。** 症状は「受信 0・送信 0」で、
**PCAN も途中 2 回モータを見失った**（アナライザが誤ったビットレートでエラー
フレームを出し、その後 bus-off で黙ったと整合する）。**まず配線 3 本
（GND を忘れやすい）と `120Ω` ジャンパを確認すること。**

**落とし穴 3: ACK が無いので、沈黙の原因を絞れない。** 配線不良・シリアル設定違い・
ビットレート違い・個体不良・そもそも探した ID にモータがいない — **全部同じ症状**。
2026-08-06 にこれで 1 晩使った。

**対策はループバック。コマンド 1 つになっている:**

```powershell
robstride-cli interfaces --selftest usbcan:COM1     # damiao-cli / myactuator-cli も同じ
```

設定コマンドの mode に `0x01` を入れると、送ったフレームがそのまま返ってくる。
**バスもモータも PCAN も要らない。** 通れば**シリアルリンク（両方向）・
2 Mbaud/2 stop bits・設定コマンドの受理・データフレームの形式・個体の健全性**が
すべて確認でき、**残る疑いは CAN 側だけ**（配線・終端・ビットレート・ID 範囲）。
落ちればワイヤを見るのをやめてシリアル設定を見る。

**PCAN が無い場所での切り分けはここから始めること。** 手で確かめたときの実測:

```
送信: AA C2 23 01 DE AD 55
受信: AA C2 23 01 DE AD 55   ← 完全一致
```

1 プロセスで送受信する。**1 つの COM ポートの所有者は 1 つ**なので、2 つの端末で
「送る側」と「聞く側」に分ける方法は使えない。

**設定コマンドのバイト 4 は `STANDARD`(0x01)。** 当初 `EXTENDED`(0x02) を入れていたが、
リファレンスは常に 0x01 を渡している。フィルタ・マスクが 0 なので無害な可能性も
あるが、**根拠があるのは 0x01 のみ**。

#### スキャン範囲で 1 晩使った（2026-08-06）

**モータが id 96 にいて、既定のスキャン範囲は 1〜32 だった。** それだけ。
ビットレート 6 種、シリアル設定、ループバック、配線見直しを順に潰したあとで
`--from 90 --to 120` で即座に見つかった。

**「no motors found」が「いない」と読めることが原因。** 実際は「見た範囲にはいない」で、
RobStride の ID は 1〜127 なので**既定は空間の 1/4 しか見ていない**。
CLI と GUI の両方で範囲を明示し、足りなければ 127 まであることを言うようにした
（`6589a77`）。**既定値は変えていない** — 127 個を per-id タイムアウトで舐めると遅く、
「速い既定 + 正直なメッセージ」の方が良い。

### 実機

**RobStride の param table 読み出しがモータを黙らせる。** **3 回再現**、電源再投入が
必要。`AppCodeName` が `"moto"` と 1 文字切れて返るのと同時に起きた。
→ 接続経路から外し、`identify --deep` で明示指定時のみ。

**3 回目（2026-08-05）で経路が確定した。`identify` は安全、`version` が黙らせる。**
名前が似ていて紛らわしいが**別の交換**である:

| サブコマンド | 実装 | 経路 | 結果 |
|---|---|---|---|
| `identify` | `read_version()` | comm type 26 | **安全**。`0.4.1.32` と完全な 4 成分が返る |
| `version` | `read_firmware_version()` | **バルク param table** | **黙る。** しかも `AppCodeVersion=0.4.` と**切り詰められる** |

つまり `identify` の方が**安全な上に答えも良い**。`version` に用は無い。
`--deep` を付けなくても `version` は危険で、そこを取り違えた（`--deep` の警告文だけ
読んで安全側にいるつもりだった）。**症状は終了時の
`disable on drop failed: timeout` に先に出る** — これが出たらそのモータはもう
黙っていると考えてよい。2 台に順に叩いて 2 台とも黙らせた。
`version` 実行前に警告と確認を入れた（2026-08-05）。

## 8. 判断の記録（蒸し返さないため）

### Params は読み取り専用（GUI と `Actuator` トレイトについて）

`Actuator::read_parameters(deep)` に書き込みの対はない。

**根拠（正確に）**: 実機ファームとマニュアルの対応が 84 行中 32 行食い違っている。
テーブルを信じて `0x2009`（マニュアルは `motor_baud`）に書くと実際は `CAN_ID` に
着弾すると**予測される**。これは実施していない。一方、**専用の `set_device_id`
フレームでの ID 変更では実際に RS-04 が 1 日応答しなくなった**。予測と実例は別物だが、
失敗様式は同じ。

**ただし `damiao-cli reg-write` は既に無検証で存在する**（§2）。「書き込み経路は無い」
のは GUI とトレイトの話であって、プロジェクト全体ではない。

### 非公式アドレス空間は既定オフ

RobStride の param table と MyActuator の `0xC0`。ここにしかない値がある
（reduction ratio、`KT_OUT`）が、前者はモータを黙らせる実績がある。

### Characterize は `SafetyLimits::gentle()`

ワークスペース最小のモータ（DM-J3507、定格 0.8 N·m）基準。**GUI は何が繋がって
いるか知らない。** ただし §2 のとおり、この枠は RS-04 では実効性が乏しい。

### 表示の誠実さ

繰り返し出てきた判断軸。**測定でないものを測定のように見せない。**

- 応答が excitation の 1/1000 以下なら「−240 dB のボード線図」ではなく
  「軸が動かなかった」と言う
- レート不足なら信用できる帯域を明示する
- 分解能が 1°/LSB なら小数 3 桁で出さない
- 無応答レジスタは空欄ではなく理由を出す
- フォールト語のビットが 1 つもマップできなければ「異常なし」と言わない
- 欠落したフィードバックは握り潰さず件数を報告する

**この文書自身が初版でこれに違反していた** — 推測を実測として書き、n を書かずに
点推定を出し、未検証を検証済みとしていた。要約は原典より不正確になりやすい。
**迷ったら原典へ。**

### Multi タブ: 残っている実機確認（次回はここから）

**同一ベンダー 2 台は 2026-08-05 に済んだ**（§4 に数値と手順）。以下は続き。
**順番に意味がある。** 段を飛ばすと、宛先の取り違えと配線不良と設定ミスが混ざって
切り分けられなくなる。

**前提: 既知の構成。** RS-04 が id 2（`0.4.1.32`）と id 3（`0.4.1.35`）。
**`version` は使わないこと**（§6）。型番は `identify` で取れるし、この 2 台は分かって
いる。インタフェースは `pcan:usb1`、classic 1 Mbps。

**0. `stop_all` を実機で確認**（§9 の表の最上段）。起動 → Multi 接続 → Enable all →
Start streaming → **右上の大きい STOP**。止まればよい。**修正前はこれが無反応だった**
ので、押して止まることを一度見ておく。変位はゼロで済む。

**1. 終端を数える。** モータを足すのは分岐を足すこと。**バス全体で終端は 2 個**。
2ch 目のキャプチャを足したときに 3 個以上になった疑いが残っている（下記）ので、
複数モータで最初に疑うのはここ。**3 台目を足す前にここを確認する。**

**2. ベンダー混在。** RobStride + MyActuator。どちらもスキャンで通電しないので、

- **型番判別が混在で狂わないか。** スキャンは Sim → Robstride → Myactuator → Damiao の
  順に走る。RobStride の応答を MyActuator として拾わないこと
- **ID 空間が衝突しないか。** MyActuator の応答は `0x240 + id`、RobStride は
  `[comm_type][extra_data][device_id]`。同じワイヤ上で紛れないこと
- **宛先テストは通電せずにできる**（下記のひな型）

**3. 3 台以上。** 2 台で 145〜154 Hz/台だったので、**台数とレートの関係を測る**。

**`dea7d0f^` で取り違えが実際に起きることは見ていない**。やるなら
`git worktree` にその親を出して `robstride-cli` を建て、id 2 を読みながら id 3 の軸を

### DAMIAO FD 欠落: 再開するときの手順

**主問題は §4 で決着済み**（モータが受信・ACK して答えていない）。以下は残件を
追う場合の手順。

**1. 監視の配線を疑う。** 応答側キャプチャの不整合は、2ch 目を足したことで終端が
3 個以上になっている可能性が第一候補。

```powershell
# 監視を外した状態。16% に戻るか
damiao-cli -i "pcan:usb1@1M,5M" --fd -m 16 --read-attempts 1 params
```

戻るなら配線が原因で、キャプチャの応答側は信用できない。戻らないなら別の要因。

**2. 観測しながら測る。**

```powershell
# 窓 1（先に起動）。PowerShell のスクリプトブロック内では -i をクォートすること
damiao-cli -i "pcan:usb2@1M,5M" --fd dump --allow-error-frames --duration 30 > capture.txt
# 窓 2
damiao-cli -i "pcan:usb1@1M,5M" --fd -m 16 --read-attempts 1 params
```

**両方の出力を突き合わせること。** 片方だけでは、監視の取りこぼしと実際の欠落を
区別できない（一度それで誤読しかけた）。

なお `rx_overruns()` / `rx_skipped()` は `CanBus` の既定実装つきメソッドなので、
SLCAN / SocketCAN では常に 0 を返す。**0 は「報告が無い」であって
「起きていない」ではない** — PCAN 以外で測っても意味は無い。

### RS-04 Sysid

前回は既定値（0.15 rad / 30 Hz / max speed 5）で走らせ、**速度上限で飽和**した。
`2πfA = 5` より **5.3 Hz 以上は速度制限が支配**する。

推奨: **amplitude 0.05 rad / f end 20 Hz / max speed 8 rad/s**
（`8/(2π×0.05) = 25.5 Hz` なので全域が有効域に入る）。

**注意点**:
- 振幅を 0.15 → 0.05 rad にすると **SNR が 9.5 dB 落ちる**。コヒーレンスが
  もともと弱い高域で効くので、**撮ったらまずコヒーレンスを見ること**
- 前回の実効レートは **144 Hz**（要求 500 Hz の 29%）。RobStride の位置モードは
  1 サンプルあたりパラメータ書き込み 2 回＋読み戻しなので落ちる。
  アプリ自身の基準（`achievedRateHz/5`）では信用できるのは 28.8 Hz まで
- 20 Hz は 144 Hz に対し 7.2 サンプル/周期で、ちょうど境界

**前回の解析について**: 「むだ時間 τ ≈ 60 ms」と書いたが、**支持できない**。
(a) 導出に使った 10 Hz は自分で「有効域は 5.3 Hz まで」と書いた外側、
(b) プラント自身の位相遅れを差し引かず全位相を遅延に帰属させている
（1 次系を仮定すると τ は 41 ms、2 次系なら 14 ms と 4.5 倍ぶれる）、
(c) 位相アンラップは隣接ビン差分なので、コヒーレンスの低い区間で 1 回滑ると
τ が 100 ms ずれる、(d) コヒーレンス値を記録していない。

**−3 dB ≈ 1.5 Hz** のほうが有効域内なのでまだ信頼できるが、これも単発・
コヒーレンス不明・生データ未保存。**§4 の他の数値と違い、この節の数値には
裏付けファイルが無い。** 撮り直したら CSV を `doc/data/` に残すこと。
